# Практична робота № 6

## Тема: Комунікація в реальному часі засобами SSE та WebSockets

---

## Мета роботи

- Опанувати технологію Server-Sent Events (SSE) для організації однонапрямленої потокової доставки подій та телеметрії від сервера до клієнта через HTTP-інтерфейс `http.Flusher`.
- Засвоїти специфікацію повнодуплексного протоколу WebSocket (RFC 6455) та механізм переведення протоколів (HTTP Upgrade) за допомогою бібліотеки `gorilla/websocket`.
- Навчитися реалізовувати масштабований архітектурний патерн Hub для централізованої реєстрації, дереєстрації клієнтів та широкомовної розсилки повідомлень (Broadcasting) через канали Go.
- Опанувати розділення логіки обробки з'єднань на незалежні горутини читання (`readPump`) та потокобезпечного запису (`writePump`).
- Реалізувати тематичні кімнати комунікації (Rooms) та механізм контролю життєздатності з'єднань (Heartbeat Ping/Pong).

## Короткі теоретичні відомості

### 1. Однонапрямлений потік подій Server-Sent Events (SSE)

**Server-Sent Events (SSE)** — це стандарт передачі текстових повідомлень від сервера до клієнта через єдине довготривале HTTP-з'єднання. Клієнт відкриває стандартний HTTP GET-запит, а сервер утримує з'єднання відкритим, надсилаючи нові фрагменти даних у міру їх появи.

Ключові технічні вимоги до SSE:
- HTTP-заголовки:
  - `Content-Type: text/event-stream` — інформує клієнта про потоковий формат;
  - `Cache-Control: no-cache` — забороняє кешування проміжними проксі-серверами;
  - `Connection: keep-alive` — утримує TCP-сесію відкритою.
- Формат повідомлень: текстовий блок, що починається з префікса `data: ` та завершується подвійним переводом рядка `\n\n`.
- Інтерфейс `http.Flusher`: стандартний механізм Go для примусового виштовхування буферизованих байтів безпосередньо в мережевий сокет без закриття відповіді.

```go
flusher, ok := w.(http.Flusher)
if !ok {
    http.Error(w, "Streaming unsupported", http.StatusInternalServerError)
    return
}

w.Header().Set("Content-Type", "text/event-stream")
w.Header().Set("Cache-Control", "no-cache")
w.Header().Set("Connection", "keep-alive")

// Надсилання події
fmt.Fprintf(w, "data: %s\n\n", `{"status":"active"}`)
flusher.Flush()
```

### 2. Протокол WebSocket та процедура оновлення з'єднання (Upgrade)

На відміну від SSE, **WebSocket** є повнодуплексним протоколом, що забезпечує двосторонній обмін фреймами між клієнтом і сервером з мінімальними накладними витратами (розмір заголовка фрейму становить лише 2–14 байтів).

Встановлення з'єднання починається зі звичайного HTTP-запиту клієнта з заголовками:
- `Upgrade: websocket`
- `Connection: Upgrade`
- `Sec-WebSocket-Key: <base64_ключ>`

У Go для перетворення HTTP-з'єднання на повноцінний WebSocket застосовується об'єкт `websocket.Upgrader` з бібліотеки `github.com/gorilla/websocket`:

```go
var upgrader = websocket.Upgrader{
    CheckOrigin: func(r *http.Request) bool {
        return true // Дозволяє підключення з будь-яких джерел (CORS)
    },
}

func wsHandler(w http.ResponseWriter, r *http.Request) {
    conn, err := upgrader.Upgrade(w, r, nil)
    if err != nil {
        log.Printf("Upgrade failed: %v", err)
        return
    }
    defer conn.Close()
}
```

### 3. Архітектурний патерн Hub та потокобезпека з'єднань

Об'єкт `*websocket.Conn` **не є потокобезпечним** для одночасного виклику операцій запису з декількох горутин. Для безпечного масштабування використовується патерн **Hub**:
1. **Горутина `readPump`:** безперервно вичитує повідомлення з сокета (`conn.ReadMessage()`) та передає їх у канал диспетчера `hub.broadcast`.
2. **Горутина `writePump`:** вичитує повідомлення з буферизованого каналу клієнта `client.send` і послідовно записує їх у сокет (`conn.WriteMessage()`).
3. **Диспетчер `Hub`:** працює в окремій горутині, координуючи додавання клієнтів, їх видалення та розсилку повідомлень за допомогою оператора `select`.

---

### 4. Контроль з'єднань Heartbeat (Ping/Pong)

Для виявлення "завислих" клієнтів (наприклад, раптове вимкнення пристрою або втрата Wi-Fi без надсилання FIN-пакета) використовується періодичне надсилання Ping-фреймів. Якщо клієнт не надсилає відповідний Pong-фрейм у межах встановленого дедлайну (`SetReadDeadline`), з'єднання примусово закривається, звільняючи пам'ять і дескриптори сокетів на сервері.

## Постановка задачі

У диспетчерських системах оперативного керування (наприклад, моніторинг серверної інфраструктури або пульт чергового інженера) виникає потреба поєднання двох різних режимів передачі даних:
1. **Однонапрямлена трансляція телеметрії (SSE):** чергова вебпанель повинна безперервно отримувати системні метрики сервера (навантаження, кількість активних горутин, мітки часу) з мінімальними витратами ресурсів;
2. **Інтерактивна координація операторів (WebSockets):** інженери повинні мати двосторонній канал оперативного зв'язку та оповіщення з можливістю підключення до тематичних кімнат (наприклад, кімната термінових аварій або загальний чат) та миттєвим поширенням повідомлень усім активним учасникам.

Необхідно розробити **сервіс моніторингу та оперативного зв'язку реального часу (Real-Time Operations Gateway)**, що поєднує в собі SSE-стрімінг метрик, повнодуплексний WebSocket-сервер на базі патерну Hub із підтримкою тематичних кімнат, механізм контролю з'єднань Heartbeat та тестову клієнтську вебсторінку для перевірки.

    - Створити точку входу `main.go`.
2. **Реалізація SSE-обробника потокових метрик:**
    - Зареєструвати HTTP-маршрут `GET /api/v1/metrics/stream`.
    - Перевірити підтримку потокового виведення через приведення типу до інтерфейсу `http.Flusher`.
    - Встановити обов'язкові службові заголовки: `text/event-stream`, `no-cache`, `keep-alive`.
3. **Організація циклу трансляції подій:**

4. **Контроль життєвого циклу клієнтського запиту:**

    - При закритті вкладки або завершенні запиту клієнтом коректно зупиняти таймер (`ticker.Stop()`) та завершувати обробник без витоку горутин у пам'яті.
5. **Тестування:**
    - Перевірити неперервний потік подій у терміналі за допомогою утиліти `curl` без буферизації:
        ```bash
        curl -N http://localhost:8080/api/v1/metrics/stream
        ```
    - Переконатися, що нові рядки з'являються щосекунди без переривання сесії.

### Рівень 2. Ключовий: Повнодуплексний WebSocket-сервер та патерн Hub (Broadcast)

1. **Збереження функціональності Рівня 1.**
2. **Встановлення та налаштування бібліотеки Gorilla WebSocket:**
    - Встановити залежність:
        ```bash
        go get github.com/gorilla/websocket
        ```
    - Ініціалізувати об'єкт `websocket.Upgrader` з налаштуванням `CheckOrigin` для дозволу з'єднань із будь-яких доменів.
3. **Реалізація архітектурного патерну Hub:**
    - Описати структуру `Hub`:
        - мапа зареєстрованих клієнтів `clients map[*Client]bool`;
        - канал для широкомовних повідомлень `broadcast chan []byte`;
        - канал для реєстрації нових клієнтів `register chan *Client`;
        - канал для видалення клієнтів `unregister chan *Client`.
    - Реалізувати метод `Run()` для диспетчера Hub, який у нескінченному циклі через оператор `select` обробляє:
        - додавання нового клієнта до мапи;
        - видалення клієнта із закриттям його персонального каналу відправки;
        - отримання повідомлення з каналу `broadcast` та його ретрансляцію в канали `send` усіх підключених клієнтів.
    - Запустити диспетчер Hub в окремій горутині у функції `main()`.
4. **Проєктування клієнтського обробника (Client Pumping):**
    - Описати структуру `Client`: посилання на `Hub`, з'єднання `*websocket.Conn` та буферизований канал відправки `send chan []byte` (місткістю 256 повідомлень).
    - Реалізувати метод `readPump()`:
        - у циклі вичитувати повідомлення з сокета за допомогою `conn.ReadMessage()`;
        - при отриманні повідомлення передавати його в `hub.broadcast`;
        - при виникненні помилки читання або закритті сокета ініціювати дереєстрацію клієнта через `hub.unregister`.
    - Реалізувати метод `writePump()`:
        - вичитувати повідомлення з каналу `client.send`;
        - записувати їх у WebSocket через `conn.WriteMessage(websocket.TextMessage, message)`.
5. **Створення ендпоінту підключення:**
    - Зареєструвати маршрут `GET /api/v1/ws`.
    - Виконувати апгрейд з'єднання через `upgrader.Upgrade`.
    - Створювати екземпляр `Client`, реєструвати його в Hub, запускати `writePump()` в окремій горутині та блокуюче викликати `readPump()`.
6. **Тестування:**
    - Відкрити два окремі термінали та підключитися через утиліту `wscat` (або `websocat`):
        ```bash
        wscat -c ws://localhost:8080/api/v1/ws
        ```
    - Надіслати тестове повідомлення з першого термінала та переконатися, що воно миттєво з'являється у другому терміналі.

### Рівень 3. Просунутий: Тематичні кімнати (Rooms), Heartbeat Ping/Pong та вебклієнт

1. **Збереження функціональності попередніх рівнів.**
2. **Організація тематичних кімнат комунікації (Room Management):**
    - Додати до структури `Client` текстове поле `room string`.
    - При підключенні витягувати назву кімнати з query-параметра запиту (наприклад, `/api/v1/ws?room=alerts` або `/api/v1/ws?room=general`). Якщо параметр відсутній — призначати кімнату за замовчуванням `general`.
    - Модернізувати структуру повідомлення, додавши інформацію про цільову кімнату та відправника.
    - У диспетчері Hub ретранслювати отримане повідомлення виключно тим клієнтам, які належать до тієї ж кімнати, що й відправник.
3. **Контроль життєздатності з'єднань (Heartbeat Ping/Pong):**
    - Налаштувати періодичне надсилання службових Ping-фреймів сервером:
        - у горутині `writePump` створити тикер з інтервалом 30–50 секунд;
        - надсилати фрейм `conn.WriteMessage(websocket.PingMessage, nil)`.
    - У горутині `readPump` налаштувати дедлайн читання (`conn.SetReadDeadline`) та обробник відповідей Pong (`conn.SetPongHandler`):
        - при отриманні кожного Pong-відгуку від клієнта продовжувати термін дедлайну читання;
        - якщо клієнт не відповів протягом таймауту — виходити з циклу читання, примусово закриваючи "завислий" сокет.
4. **Створення демонстраційної вебсторінки (Web Client):**
    - Створити окрему статичну HTML-вебсторінку (наприклад, `web/index.html`), яка містить два інтерактивні блоки:
        - **Панель телеметрії (SSE):** підключається через стандартний браузерний API `new EventSource('/api/v1/metrics/stream')` та в реальному часі оновлює показники пам'яті й горутин;
        - **Пульт оперативного зв'язку (WebSocket):** поле вибору кімнати (`room`), підключення через `new WebSocket(...)`, поле введення повідомлень та вікно логу чату.
    - Налаштувати віддачу статичних файлів у сервері Go (`http.FileServer` або роут `r.Static`).
    - Відкрити вебсторінку у двох вкладках браузера, підключитися до однакових і різних кімнат та продемонструвати викладачеві роздільну розсилку подій.

## Критерії оцінювання

Оцінювання здійснюється за шкалою повноти реалізації рівнів практичної роботи:

- **«Задовільно» (Рівень 1):** реалізовано базовий прототип, створено структуру проєкту, програма успішно компілюється та виконує базові сценарії.
- **«Добре» (Рівень 2):** виконано базовий рівень та реалізовано ключову функціональність заняття, забезпечено надійність і безпеку виконання коду.
- **«Відмінно» (Рівень 3):** повністю завершено всі три рівні завдання з дотриманням кращих інженерних практик, чистоти архітектури та оптимізації.
- **Усний захист:** обов'язкове пояснення логіки коду та впевнені відповіді на контрольні питання викладача.

## Вимоги до звітності

1. Опублікувати вихідний код у Git-репозиторії.
2. Оформити файл `README.md` з описом проєкту, інструкцією запуску та обов'язковими скриншотами роботи програми (включаючи демонстрацію відсутності помилок).
3. Продемонструвати роботу програми викладачеві та захистити результати.
